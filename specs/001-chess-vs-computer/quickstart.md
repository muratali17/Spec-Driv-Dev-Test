# Quickstart & Validation Guide: Browser Chess vs Computer

**Feature**: `001-chess-vs-computer`
**Plan**: [plan.md](./plan.md)

This guide explains how to run the prototype and how to validate it end-to-end.
It is a run/validation guide, not an implementation walkthrough; details of the
data model and interfaces live in [data-model.md](./data-model.md) and
[contracts/](./contracts/).

---

## Prerequisites

- Node.js 20+ and npm.
- A modern Chromium/Firefox/WebKit browser.
- One-time browser install for automation:
  ```bash
  npx playwright install --with-deps chromium
  ```
  (Install the other engines only if cross-browser runs are desired.)

No backend, database, or API keys are required.

---

## Install and run

```bash
npm install                 # installs deps, including the stockfish package
npm run dev                 # copies public/engine/*, starts Vite dev server
```

Open the printed local URL. The board should show the standard start position with
white at the bottom, no difficulty selected, and the phase in `setup`.

### Engine asset note

`public/engine/` is generated by `scripts/copy-engine.mjs` (run automatically by
`predev`, `prebuild`, and `pretest`). It copies only
`stockfish-19-lite-single.js` and `stockfish-19-lite-single.wasm` from the
`stockfish` package. The directory is git-ignored. To regenerate manually:

```bash
npm run copy-engine
```

If the engine worker cannot load, verify both files exist in `public/engine/` and
that they are served from the same path (the engine resolves the WASM from its own
`.js` URL).

## Build static output

```bash
npm run build               # emits static assets to dist/
npm run preview             # serve dist/ locally
```

`dist/` is fully static and needs no special headers.

## Automated acceptance tests

```bash
npm run test:e2e            # Playwright builds/serves the app and runs tests
npm run test:e2e -- --ui    # optional interactive runner
```

`playwright.config.ts` provides a `webServer` so tests start deterministically with
no manual setup (Constitution Principle XII). `testIdAttribute` is
`"data-testid"`.

Tests are derived from the specification acceptance scenarios and organized as:

| Spec | Test file |
|---|---|
| US1 start + difficulty | `tests/e2e/start-game.spec.ts` |
| US2 legal/illegal moves | `tests/e2e/legal-illegal-moves.spec.ts` |
| US2 thinking/blocking/reply | `tests/e2e/computer-turn.spec.ts` |
| US2/US3 history + status | `tests/e2e/history-status.spec.ts` |
| US4 restart | `tests/e2e/restart.spec.ts` |
| US3 check/checkmate/stalemate + no moves after end | `tests/e2e/game-end.spec.ts` |
| US5 promotion/castling/en passant | `tests/e2e/special-moves.spec.ts` |
| US6 mobile viewport | `tests/e2e/mobile.spec.ts` |

### Generated engine-move fixtures

The curated-difficulty tests depend on expected engine moves for the pinned
version:

```bash
npm run generate:engine-fixtures   # writes tests/fixtures/engine-moves.ts
```

Run this after any `stockfish` version bump, review the diff, and commit it. The
generated file records, per FEN and per difficulty, the expected UCI move produced
by the `ucinewgame` + `Clear Hash` + `go depth` protocol. See research R3.

## Manual validation checklist

Use this to confirm the observable contract before/after implementation. Each item
maps to the selectors in [contracts/ui-observability.md](./contracts/ui-observability.md).

### Start and difficulty (US1)

1. On load: `[data-testid="game-status"]` shows `data-phase="setup"` and no
   difficulty selected.
2. Click **Start Game** with no difficulty: game does not start;
   `[data-testid="message"]` says a difficulty must be selected.
3. Select **Medium**, click **Start Game**: `data-phase="playing"`,
   `data-turn="white"`, board in the standard start position, and
   `data-difficulty="medium"`, `data-engine-depth="4"`.
4. While playing, difficulty controls are unavailable; the current difficulty is
   displayed.

### Legal and illegal moves (US2)

1. Click the white `e2` pawn, then `e4`: the pawn moves; `data-turn="black"`.
2. Click a white piece, then an illegal target: board unchanged, `data-turn`
   stays, and a message appears.
3. Clicking a black piece selects nothing.

### Thinking state, blocking, reply (US2, SC-004, SC-005)

1. After a legal white move, `data-thinking` becomes `"true"` and
   `[data-testid="thinking-indicator"]` is visible.
2. While it is `"true"`, clicking white pieces does nothing.
3. When `data-thinking` returns to `"false"`, exactly one legal black move is on
   the board and `data-turn="white"`.
4. Using the browser console, observe the `data-thinking` true→false interval and
   confirm it is `>= 250 ms` (the Playwright suite asserts this automatically).

### History and status (US2, US3)

1. Each move appears once in `[data-testid="move-history"]`, in order, with
   `data-side` reflecting who moved.
2. Status always reflects turn, thinking, and any check/result.

### Restart (US4)

1. Make several moves, click **Restart Game**: board resets, history clears,
   `data-phase="setup"`, `data-difficulty="none"`.
2. Restart while the indicator is visible: the board resets and **no** stale
   computer move is applied.

### Check, checkmate, stalemate (US3)

Use the `?fen=` test hook to seed positions (URL-encoded):

- Human checkmates: `/?fen=<white-to-move mate-in-1>&difficulty=easy`, start, play
  the mating move; `data-result="checkmate"`, `data-winner="white"`.
- Computer checkmates: `/?fen=<black-to-move mate-in-1>&difficulty=easy`, start;
  the computer mates; `data-result="checkmate"`, `data-winner="black"`.
- Stalemate: seed a stalemated side-to-move position; after resolution
  `data-result="stalemate"`, `data-winner="none"`.
- After any terminal state, clicking the board changes nothing.

### Special moves (US5)

- **Promotion:** seed a white pawn on the 7th with a clear path, move it to the
  last rank; `[data-testid="promotion-dialog"]` appears and the turn does not
  advance until a piece is chosen.
- **Castling:** seed a position with king and rook unmoved and the path clear;
  move the king two squares; king and rook both move and the move is recorded.
- **En passant:** seed a position with a black pawn that just advanced two squares
  beside a white pawn; capture to the en-passant square; the black pawn is removed.
- Attempt each move illegally: it is rejected exactly like any illegal move.

### Mobile viewport (US6)

1. Set the viewport to 480 px, then 375 px, then 320 px.
2. Confirm no horizontal scroll
   (`document.documentElement.scrollWidth <= window.innerWidth`).
3. Start a game, make a legal move, and read status/history at each width.

## Agent-driven browser validation (Playwright MCP)

Beyond the automated suite, the running app can be exercised interactively with
Playwright MCP during development:

1. Start the dev server (`npm run dev`).
2. Use Playwright MCP to navigate to the local URL and drive the same accessible
   selectors (`game-status`, square `data-square`, difficulty buttons, etc.).
3. Verify the thinking indicator, blocking, computer reply, restart, and the
   seeded special-move positions interactively.

Both automated and agent-driven validation share the contract in
[contracts/ui-observability.md](./contracts/ui-observability.md), so they cannot
drift apart.

## Success signals

- `npm run build` produces static `dist/` with no backend and no special headers.
- `npm run test:e2e` passes; the thinking-duration and difficulty-fixture tests
  pass deterministically across repeated runs.
- Manual checklist items above all hold, including at 320 px width.
